# ED Helper v1.11 — Trade route pad-size verification

**Date:** 2026-07-27
**Status:** Approved (Brian's bug report: Type-6 [M pad] routed to a small-dock
facility; "It needs to be considered in the route destinations.")
**Probe-verified** (findings doc "Pad sizes" section, fixture
`station-search-pads.json`): the trade API's ONLY pad lever is binary
`requires_large_pad`; hop objects carry NO pad fields; `/stations/search`
records DO carry `has_large_pad` + `large_pads`/`medium_pads`/`small_pads`
counts (null-guard them) and pad filters work. Station `type` is NOT reliable
(live counterexample recorded). Spansh's own site shares this blind spot — we
fix it client-side.

## Decisions (recommended defaults)

| Topic | Decision |
|---|---|
| Fit test | Ship pad M fits when `(medium_pads ?? 0) > 0 \|\| (large_pads ?? 0) > 0 \|\| has_large_pad === true`. Pad S always fits; pad L keeps today's `requires_large_pad=1` (server-guaranteed, no verification needed). |
| Where | Host `plotTrade`: after mapping, when `padSize === 'M'`, resolve each unique hop station via `/stations/search` (filters name + system_name; disambiguate by matching `market_id` when present; cache per plot). Annotate hops: `padFit?: boolean`, `pads?: { small, medium, large }`. Lookup failure → `padFit` left undefined (unknown ≠ bad). |
| Types | Engine `Hop` gains the two OPTIONAL fields (additive; existing tests unmodified). |
| UI | TradePlanner plan + checklist rows: red `NO M PAD` badge on hops with `padFit === false`; when any hop fails, a warning banner above the plan: "⚠ <n> stop(s) have no Medium pad — this route won't fully work for your ship. Consider re-plotting with pad size Large (stricter but guaranteed)." Unknown pads show a dim `PAD?` badge. START stays enabled (partial routes still useful; the banner explains). |
| Non-goals | No route truncation/auto-replot; no changes for S/L ships; station pad data cached only per plot (no persistence). |
