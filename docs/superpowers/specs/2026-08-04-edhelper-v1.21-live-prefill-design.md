# ED Helper v1.21 — Trade Planner start fields follow the live ship

**Date:** 2026-08-04
**Status:** Implemented

## Problem

Reported by CMDR GORIGNA:

> "When pressing clear route, the ship location, money, etc at the top needs to be refreshed."
> "It comes from finishing the route, and wanting to generate a new one, the location and money doesn't update."
> "If I change tabs and back, it refreshes."

After running a trade route to completion and clearing it, the Trade Planner still showed
the system, station and credit balance from where the route was originally plotted. Plotting
a follow-up route therefore started from a system the ship had long since left, and budgeted
with a stale credit balance — Spansh returns a plausible-looking route that begins hundreds
of light years away.

## Investigation

Ruled out first, because the obvious suspects were innocent:

- **`JournalWatcher`** (`packages/engine/src/journal/watcher.ts`) re-scans for the newest
  journal file on every 1 s poll, resets its cursor across file rotation, and emits `'state'`
  whenever a parsed event changes state. It was reporting the ship correctly the whole time.
- **`CockpitPanel`** renders `ship.system` / `ship.station` / `ship.credits` straight from
  props with no local copy, so the left-hand card was already live.

The commander's third message is the decisive clue: switching tabs unmounts `TradePlanner`
and destroys its `useState` values, so remounting re-runs the prefill against a blank form.
That points at component-local state, not at the data pipeline.

Root cause, `packages/app/src/renderer/src/components/TradePlanner.tsx`: the prefill effect
filled a field only when it was empty.

```tsx
setFromSystem((v) => (v === '' && ship.system ? ship.system : v));
```

Once the first plot had populated the form, every field was permanently frozen for the
lifetime of the component.

## Design

The start fields **follow the live ship until the commander edits them.**

Ownership is tracked per field with a `touched` record, extending the mechanism the pad-size
select has always used: the first edit to a field stops it following, permanently. Nothing
auto-fills a field the commander has typed into — including one they deliberately cleared.

```tsx
const [touched, setTouched] = useState({
  system: false, station: false, cargo: false, capital: false, pad: false,
});

function touch(field: keyof typeof touched) {
  setTouched((t) => (t[field] ? t : { ...t, [field]: true }));
}
```

An earlier draft inferred "touched" by comparing each field against the last value the
component auto-filled. That reads well but is wrong in two ways: typing a value that happens
to equal the live one silently forfeits ownership, and — because the field values then have
to be effect dependencies — clearing a field re-fires the effect and refills it on the same
keystroke, making the fields impossible to blank. An explicit flag is exact.

### System and station move as a pair

They are followed together and only while docked:

```tsx
if (ship.docked && ship.system && ship.station && !touched.system && !touched.station) {
  setFromSystem(ship.system);
  setFromStation(ship.station);
}
```

An undocked ship reports a system but no station. Following the two independently would leave
the form showing a new system next to the station the ship just left — a market that doesn't
exist. Spansh answers that with an empty result rather than an error (see the silent-ignore
note in `docs/superpowers/notes/2026-07-24-spansh-api-findings.md`), so the commander would
see "No profitable route found" with nothing pointing at the real cause. Editing either field
freezes both.

### Rejected alternatives

- **Reset the form in `onClear`** — only fixes the clear-route path. The fields are equally
  stale if the commander plots, flies somewhere else, and comes back without ever starting
  the route.
- **Remount the component on clear (`key` prop)** — would also discard hand-typed pad size,
  hop count and range settings, which the commander expects to persist.

### Fields covered

| Field | Follows ship | Notes |
|---|---|---|
| Start system | ✅ | Only while docked, paired with station |
| Start station | ✅ | Only while docked, paired with system |
| Cargo (t) | ✅ | Free space (v1.14 behaviour). A full hold has no free space, so the field is left alone rather than filled with `0`, which would only fail validation on PLOT |
| Capital (cr) | ✅ | `ship.credits`; position-independent, so it follows in flight too |
| Pad size | ✅ | Unchanged behaviour, now sharing the `touched` record |
| Range / hops / max age / checkboxes | ❌ | Commander preferences, never auto-filled to begin with |

## Testing

Seven component tests in `packages/app/tests/components.test.tsx`:

1. Rerendering with a moved ship updates start system, station and capital, and the old
   system is gone from the form.
2. A hand-typed start system survives the ship moving.
3. A field the commander cleared stays empty — both on the keystroke and across a ship update.
4. Editing the start system freezes the station too.
5. In flight (undocked, no station) the last docked system/station pair is retained, while
   capital keeps following.
6. Cargo follows free hold space, not total capacity.
7. A full hold does not fill cargo with `0`.
