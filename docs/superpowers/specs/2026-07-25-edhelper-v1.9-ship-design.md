# ED Helper v1.9 — Ship Configure tool (profiles + auto fuel model)

**Date:** 2026-07-25
**Status:** Approved by Brian (design presented interactively; "ship profiles +
auto fuel model" scope chosen via question, design approved with "1").
**Builds on:** v1.8 (complete Spansh tool set, merged)

## Purpose

Tenth pill **SHIP**: turn the commander's real ship into the numbers the
plotters need. Three sources: (1) auto-derived from the journal `Loadout`
event, (2) pasted Coriolis/EDSY (SLEF) build passed verbatim to Spansh's
`ship_build` param, (3) manual tweaks. Named profiles persist in settings.json;
the active profile prefills the Galaxy Plotter.

## Journal facts (verify in Task 1 against the real journal — probe-first)

`Loadout` carries `UnladenMass`, `FuelCapacity: {Main, Reserve}`,
`CargoCapacity`, `MaxJumpRange`, and `Modules[]` where the FSD is
`Slot: "FrameShiftDrive"`, `Item: "int_hyperdrive_size<S>_class<C>"` (or
`int_hyperdrive_overcharge_size...` for SCO drives), optional
`Engineering.Modifiers[]` incl. `{Label: "FSDOptimalMass", Value}`. A Guardian
booster appears as `Item: "int_guardianfsdbooster_size<N>"`.

## FSD constants (well-known lookup tables — encode in engine)

- fuel_multiplier by rating (class letter C=1..A=5): E=.011 D=.010 C=.008 B=.010 A=.012
- fuel_power by size: 2→2.00 3→2.15 4→2.30 5→2.45 6→2.60 7→2.75
- optimal_mass by size/rating (standard table; engineered value OVERRIDES from
  `FSDOptimalMass` modifier), max_fuel_per_jump by size/rating (standard table).
- Guardian booster range_boost by size: 1→4.0 2→6.0 3→7.75 4→9.25 5→10.5 ly.
- SCO ("overcharge") drives use the same tables keyed by size/rating with
  `supercharge_multiplier` staying 4 (MkII overcharge = 6 is a deferred nicety).

Task 1 is probe-first: read the REAL journal Loadout from
`%USERPROFILE%\Saved Games\Frontier Developments\Elite Dangerous\` (or
EDHELPER_JOURNAL_DIR), record a fixture of the commander's actual FSD module +
mass/fuel fields, and encode the constants tables verified against public FSD
data. If the real Loadout shape differs, the fixture wins.

## Decisions

| Topic | Decision |
|---|---|
| Engine | Extend `Loadout` parsing: `unladenMass`, `fuelMain`, `fuelReserve`, `fsdItem` (raw module id), `fsdOptimalMass?` (engineered), `guardianBoosterItem?`. ShipState carries them. Existing tests unmodified; new parse/state tests. |
| Derivation | New `packages/app/src/main/ship-model.ts`: `deriveFuelModel(state) → { fuelPower, fuelMultiplier, optimalMass, baseMass, tankSize, internalTankSize, maxFuelPerJump, rangeBoost, reserveSize } | null` (null when FSD unknown). Pure function + tables, unit-tested. |
| Profiles | `ShipProfile { name, source: 'journal'|'build'|'manual', model?: FuelModelFields, shipBuild?: string (raw SLEF JSON), cargo?: number }`. Stored in settings.json (`shipProfiles: ShipProfile[]`, `activeProfile?: string`). IPC `ship:profiles:get/save/delete/activate` + `ship:model:get` (current journal-derived model). |
| Galaxy Plotter | Prefills fuel-model fields from (active profile.model) → else journal-derived → else current hardcoded defaults. When active profile has `shipBuild`, plotGalaxy sends `ship_build` verbatim INSTEAD of the numeric fields (probe-verified param) — the fuel-model group shows "Using pasted build" and is disabled. `PlotGalaxyRequest` gains optional `shipBuild?: string`. |
| SHIP view | Tenth pill. Shows current ship (name/type/mass/fuel/FSD + derived model, read-only rows), editable copy with Save-as-profile (name box), profile list (activate/delete, active highlighted), SLEF paste textarea with Save-as-build-profile. |
| Out of scope | Module-by-module outfitting; profile-driven jump-range prefills in other tools (journal prefill stays); MkII overcharge multiplier 6; auto-sync profile when ship changes. |

## Testing

Engine parse/state tests (real-journal fixture), ship-model unit tests

round-trip, host/IPC tests, component tests (SHIP view, galaxy prefill from
model, build-profile disables fields), live smoke against the real journal
